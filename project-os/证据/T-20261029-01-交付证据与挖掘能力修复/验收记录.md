# T-20261029-01 交付证据与挖掘能力修复 验收记录

> 验收时间：2026-10-29。结构化数据见[验证结果](验证结果.json)。

## 结论

上一轮遗留三项中，两项半可在本地修复。查证过程推翻了「托管 CI 纯外部阻塞」与「样本不足是纯成本」的笼统判断——两者背后各藏着一个**本地可修的实现缺陷**。

## 缺陷 1：CI 报告从未入库

`reports/runs/` 被 `.gitignore` 排除，而 `scripts/run_ci.py` 恰好写这个目录。

**后果**：我上一轮反复声称「本地 CI 8/8 通过」，但报告从未进入仓库，克隆下来的人查不到任何证据。

**修复**：

| 改动 | 内容 |
|---|---|
| 报告目录 | `reports/runs/` → `reports/ci/`（入库） |
| 稳定指针 | 额外写 `reports/ci/最新一次.json`，避免翻找时间戳文件名 |
| 回归测试 | `test_ci_report_directory_is_tracked` 等 3 条，防止再次被忽略 |

验证：`git check-ignore reports/runs/x.json` → 0（忽略）；`reports/ci/最新一次.json` → 1（未忽略）。

## 缺陷 2：挖掘结果无法提升为修复样本

`replens/miner.py` 组装输出时只保留 `id/category/issue/expected`，**主动丢弃 `commit` 与 `parent`**。

**后果**：即使验证 fail→pass 通过，也因缺 `buggy_parent`/`fix_commit` 还原不出 buggy 基线，候选永远停在「定位级」。
这直接解释了为什么 `eval/mined/` 里有 10 条已验证候选却一条都没能进入修复集。

**修复**：输出补充 `project` / `buggy_parent` / `fix_commit` / `test_files` / `src_files`。

**实测**：对本地 tqdm 挖掘 3 条，**3 条验证通过且字段完整**：

```text
挖掘到 3 条候选样本；验证通过 3 条
  [PASS] 1: contrib.concurrent: fix no-len iterables -> tqdm/contrib/concurrent.py:_min_map_len:103
  [PASS] 2: length detection in contrib.concurrent -> tqdm/contrib/concurrent.py:_executor_map:42
  [PASS] 3: rich: misc fixes -> tqdm/rich.py:render:31
```

**附带发现**：miner 要求同一次修复提交内既有源码改动、也有测试改动；只改源码不会被挖掘。这是既有行为，已写进测试注释。

> 边界：能力已打通，但这 3 条**尚未**并入 `eval/datasets/` 正式分母。并入需逐条核实来源、重复性与许可，属下一步。

## 缺陷 3：交付包无法确定性重建

`repo-control/` 原本手工整理；`使用说明.txt` 描述的 `payload/` 目录**从未随包提供**，还原流程是断的。

**修复**：新增 `scripts/build_delivery.py`，把打包脚本化，并拒绝打包非 PASS 结果。

保留策略：阶段 A 的 `manifest.json` / `使用说明.txt` / `validation/tqdm-reset-inf/` 原样保留为历史，不覆盖。
