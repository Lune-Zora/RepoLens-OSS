## 结论

三项遗留中 ②③ 已解决，① 因 ② 的修复而部分解决（requests 首条样本首次可用）。
过程中还发现并修正了一处**影响全部样本**的口径缺陷：`expected.line` 填的是改动行，而指标要求符号定义行。

## 一、纯插入 hunk 的归属

旧逻辑在 hunk 无删除行时回退到 **hunk 起始行**，而那往往只是前导上下文。

requests 的 `__reduce__` 一例：

```text
@@ -41,6 +41,16 @@ class JSONDecodeError(...):
         CompatJSONDecodeError.__init__(self, *args)      ← 上下文
         InvalidJSONError.__init__(self, *self.args, ...) ← 上下文
                                                          ← 上下文
+    def __reduce__(self):                                ← 插入从这里开始
```

前 3 行是上下文，插入实际发生在旧 43 行之后。回退到 41 会把归属算成 `__init__`（未被改动）。
修正后 `old_pos = 43`。

## 二、新增符号归到外层类

新增方法在 buggy 版本不存在，不能作为定位目标（检索永远命中不了）。规则：

1. 改动落在**已有**符号内 → 用该符号；
2. 改动**新增**了符号 → 归到其在旧版本存在的外层类；
3. 都不成立 → 退回旧文件改动位置的符号。

效果：`__init__:41` → **`JSONDecodeError:31`**。类在 buggy 版本存在，且类范围包含新增的 `__reduce__`，语义正确。

## 三、影响面最大的发现：`expected.line` 口径错了

`eval_metrics` 的行判定是 `abs(符号起始行 - line) <= 3`，即 `line` 应为**符号定义行**。
而旧挖掘器填的是**改动行**。

| 例子 | 旧标注 | 正确值 | 旧标注指向的内容 |
|---|---|---|---|
| `tqdm/std.py:format_meter` | 533 | **463** | 函数体内的 `if total and n >= (total + 0.5):` |

**后果：96 条中 85 条的标注在指标口径下必然落空。**
之前所有「定位评测」的数字若用过这份数据，行命中率都会被系统性低估。

已用 `scripts/repair_annotations.py` 全部修正。

## 四、前缀剥离规则

| 问题 | 修复 | 结果 |
|---|---|---|
| `that tqdm_class cannot be passed…` 残句 | 剥完若以虚词开头则不剥 | 恢复为 `Fix that tqdm_class cannot be passed…` |
| `ROB: Fix compatibility…` 前缀未剥 | 前缀集加入 `rob` / `hotfix` | 变为 `Fix compatibility for fonttools < 4.57.0` |

修的过程中踩到反向坑：把 `release` 当标签后，`Release content streams…` 的正文被削掉。已把 `release` / `chore` 移出前缀集。

## 五、新增工具：只重算标注

`scripts/repair_annotations.py`：不重跑测试，只按新规则重算 `expected` 与 `issue`。

为什么需要：重跑挖掘代价高（每样本两遍测试），而这两项只影响**标注文本**，不影响 fail→pass 是否成立。
