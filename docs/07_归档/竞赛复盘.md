## 二、项目现状盘点（检索证据）

### 2.1 代码规模与模块

- replens/：13 个模块，约 76KB；核心零第三方依赖（纯 Python 标准库）。
- 模块：repo（仓库导入/许可证识别）、indexer（AST+SQLite FTS5 索引）、
  retriever（BM25+调用图+证据绑定）、retriever_hybrid（BM25+向量 RRF，本次新增）、
  planner（规则/LLM 计划）、patchgen（自动补丁生成+验证闭环，本次新增）、
  testgen（回归测试生成）、executor（白名单+临时副本+超时）、
  report（报告）、llm（OpenAI 兼容客户端）、eval_runner（评测）、compliance（本次新增）。
- web/app.py：FastAPI 页面 + analyze/run 两个端点（本次增强）。
- eval/：25 条自建评测集 + eval.py + baselines.py（本次新增）。
- examples/demo_repo：4 模块、5 处真实 bug、修复补丁。

## 三、优势（国奖答辩可守住的点）

1. 设计主线清晰：让模型的每一个判断都能被代码证据和测试结果证伪或证实。
2. 定位不依赖 LLM：FTS5+调用图是确定性计算，幻觉不污染定位。
3. 离线零依赖闭环：无 key、无网络也能演示完整流程，抗现场翻车能力强。
4. 安全执行三层隔离：白名单、临时副本、超时，评委会追问的安全问题有实打实的答案。
5. 诚实拒答：证据不足明确返回"证据不足"，而不是硬答（评测拒答率 1.0）。
6. 评测框架已具雏形：多粒度指标 + 基线对比 + 消融思路。

## 四、不足清单（按对国奖的影响排序）

### P0（演示翻车级，已修复）

1. Windows GBK 控制台打印报告 UnicodeEncodeError → 已修复（cli.py 统一 reconfigure UTF-8）。
2. 项目本身不是 git 仓库，无法自证协作历史 → 已 git init 并保留提交记录。
3. 补丁必须手工提供，与项目名"补丁生成"名不副实 → 已新增 patchgen 自动补丁闭环。

### P1（评委专业追问级，部分已修复，仍需继续加强）

4. 检索只有 BM25 关键词，语义不匹配场景漏召回 → 已新增 hybrid（BM25+向量 RRF）。
5. 评测集自造、仅 25 条、只覆盖一个 4 模块玩具仓库；没有与 SOTA 工具/真实仓库对比。
6. 回归测试生成是模板化的"存在性/签名/边界"断言，不是行为断言。
7. 计划生成（RulePlanner）是模板拼接，LLM 路径没有把"计划→补丁→测试反馈"串成迭代优化。
8. Web 层只是 JSON 展示，没有证据链可视化、没有补丁 diff 展示。

### P2（竞争力级）

9. 仅支持 Python 仓库（ast 单一适配器），跨语言是空白。
10. 调用图扩展是符号名精确匹配，无别名/导入解析/继承分析，跨文件重名会误扩展。
11. 安全执行是文件+命令+超时三层，无容器/沙箱（可以文档说明 MVP 边界）。
12. 中文 Issue 分词为整串，与英文代码 token 匹配弱。
13. 无真实开源社区贡献记录（无 PR/Issue 链接），方向三评委可能追问。
14. 缺少消融实验的自动化脚本（BM25-only vs +调用图 vs +向量）。
15. 依赖披露知识库只覆盖常见包，未知包需人工确认（可接受但要在报告中说明）。

### P3（加分项）

16. 无代码仓库级问答（如"这个项目的错误处理策略是什么"）。
17. 无 PR 生成（branch + commit + GitHub API）。
18. 无多线程/大仓库性能基准。
19. 报告没有把 patch diff 直观渲染出来（JSON 补丁渲染成 diff 已有函数，但报告未调用）。

## 五、国奖对标分析（联网调研结论）

调研对象（2026 赛季公开资料）：SWE-bench / SWE-bench Verified、SWE-agent / mini-swe-agent、
OpenHands、RepoAgent（OpenBMB）、Aider、Sweep 等。

1. 通用 AI 编程智能体（SWE-agent/OpenHands/Aider）的核心是 LLM 自主循环
   （检索→改文件→跑测试→看日志→再改），强在通用性，弱在成本与不确定性。
2. RepoAgent 的核心是仓库级文档生成，其对象图（Object Graph）思路值得借鉴。
3. 大赛评审不奖励"模型大/算力多"，奖励"轻量、可验证、有真实贡献"。
   因此 RepoLens 不应去拼通用智能体，而应把「新手可验证贡献」这个定位打穿：
   - 定位可证伪（证据=文件:行号，可回溯索引）；
   - 补丁可验证（修复前 fail / 修复后 pass 的 exit code 对比）；
   - 全过程可复现（一条命令离线重放）。

## 六、创新点定位（答辩叙事主线）

1. 证据优先、可证伪的定位与修复闭环：不是"模型说在哪"，而是"证据指向文件:行号，
   测试 exit code 证明修复有效"。
2. 确定性检索 + 语义检索的 RRF 融合，且语义层为可选插件，不破坏零依赖闭环。
3. 补丁自动生成 + 结构化校验 + 测试反馈修复重试：LLM 幻觉被
   "from 串必须真实存在于文件"的校验物理拦截。
4. 三层安全执行（临时副本/命令白名单/超时）+ 原仓库不可变，可哈希证明。
5. 零 key 离线兜底：规则引擎能完成 demo 级"定位→计划→补丁→测试"全流程，
   现场答辩不依赖 API 可用性。
6. 合规自动化：LICENSE 识别 + 第三方依赖披露报告，直接回应形式审查。
