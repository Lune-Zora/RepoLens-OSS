# 人工通读记录

> 更新：2026-10-29（三轮）。对象：自动挖掘并入正式修复集的样本。**逐条通读 issue 文本与对应 diff**，判定其是否准确反映修复行为。
> 判定结果以数据形式保存：[人工复核判定.json](../../eval/datasets/人工复核判定.json)，由 `scripts/promote_mined.py` 读取执行。

## 1. 为什么要做这一步

机械复核（[评测口径总表](评测口径总表.md) 第 6 条）能验的是**事实**：提交是否存在、父子关系、标注是否被改动触及。
但它验不了**语义**：这条 issue 描述是否真的说清了这个改动在修什么。

典型反例：一条合并提交的标题 `Merge pull requests #1717 and #1767 (fixes #1658)` 完全通过机械校验——
提交存在、父子正确、标注被触及、测试也在补丁里——但它**根本不是一条 issue 描述**。
这种样本放进定位评测，等于给模型一个无意义的查询。

## 2. 方法

对每条样本调出：提交标题、issue 文本、改动文件、diff 的增删行，逐条判断：

| 判定 | 含义 | 处理 |
|---|---|---|
| 合格 | issue 能说明修复了什么行为 | 保留 |
| 弱描述 | 方向对但过于笼统，或语法不完整 | **保留**，记录在案 |
| 剔除 | 不是缺陷描述、不是行为修复，或与其他样本重复 | 不进入分母 |

## 11. 第三轮：规则修复后的问题消解（2026-10-29）

第二轮遗留 10 条弱描述。第三轮不去改写措辞，而是**修产生弱描述的规则**：

| 问题 | 根因 | 修复 | 结果 |
|---|---|---|---|
| `that tqdm_class cannot be passed…`（残句） | 剥 `Fix` 前缀后句子断裂 | 剥完若以虚词开头则不剥 | 恢复为 `Fix that tqdm_class cannot be passed…` |
| `ROB: Fix compatibility…`（前缀未剥） | 前缀集只有 fix/bug | 前缀集加入 `rob` / `hotfix` | 变为 `Fix compatibility for fonttools < 4.57.0` |

> 修的过程中又踩到一个反向坑：把 `release` 当标签后，`Release content streams…` 的正文被削掉。
> 已把 `release` / `chore` 移出前缀集——它们更常是句子开头而非类型标签。

## 12. 顺带发现的标注口径缺陷（影响全部样本）

复核第三轮时发现：`expected` 的 `line` 字段含义与指标口径不一致。

| 项 | 旧行为 | 指标要求 |
|---|---|---|
| `line` 取值 | 修改发生的行 | 符号**定义行**（`eval_metrics` 用 `abs(start_line - line) <= 3`） |

**后果**：96 条中 85 条的标注在指标口径下必然落空（例如 `format_meter` 定义在 463 行，标注却是函数体内的 533 行）。

**修复**：`attribute_symbol` 统一返回符号定义行，并用 `scripts/repair_annotations.py` 回溯修正已有样本（91/98 条被改）。

## 13. 第四轮：弱描述的出处升级（2026-10-29）

第三轮的结论是「不改写」，这话只对了一半。逐条拆开看，8 条弱描述的成因有三类：

| 成因 | 条数 | 例子 | 处理 |
|---|---|---|---|
| 被我们自己的前缀规则削成名词短语 | 5 | `fix format_num` → `format_num` | 修 `_clean_issue` 规则 3：句子式前缀剥完只剩 1-2 个词就不剥 |
| 标题只说主题，但正文有完整描述 | 2 | `shell completion for nested groups` | 取提交正文首句（仍是上游原文） |
| 标题与正文都极简，但关联 issue / PR 有原文 | 5（去重后含上两类的补充） | `speculative speculative empty string check` | 入 `eval/curation/issue_upgrade.json`：issue 标题 / PR 正文首句 + 出处 URL + 抓取日期 |
| 上游确实没有更好的文本 | 1 | `fix edge cases & windows tests` | 保留原文，标 `issue_quality: weak` |

### 关键区分：换出处 ≠ 改写

| 做法 | 是否允许 | 理由 |
|---|---|---|
| 改写措辞（人写一句更顺的） | **不允许** | 描述不再来自上游，评测集就失去可核查性 |
| 换一处上游原文（正文 / issue 标题 / PR 正文） | 允许 | 仍是上游写的字，且能回溯到具体 URL |

实现上，出处写在数据里：

| 字段 | 取值 | 含义 |
|---|---|---|
| `issue_source` | `commit_subject` / `commit_body` / `upstream_issue` / `upstream_pull` | 这段文字从哪来 |
| `issue_quality` | `clear` / `weak` | 是否仍属弱描述（保留在分母内，引用指标时须说明条数） |

> 正文只在人工判定为 `weak` 时才采用。否则启发式会把
> `pandas>=3 & negative format_interval` 这类「短但合格」的标题换成正文里的某条实现细节——
> 这是本轮实测踩到的反向坑（第 7 条）。换出处由人决定，不由启发式决定。

### 顺带修掉的两个静默缺陷

1. `_clean_issue` 里的空白折叠正则被写成了 `r"\\\\s+"`（双反斜杠），
   实际匹配的是「字面量反斜杠 + s」，标题里的连续空格从未被折叠。已改回单反斜杠并加断言测试。
2. 复核器 C6 原先只认「提交标题（或其剥前缀形式）」。本章的换出处样本必然被判「与提交标题不同」，
   故 C6 改为按 `issue_source` 取证：正文出处的必须是正文原文；上游出处的必须在
   `issue_upgrade.json` 里有对应条目。另新增 C9：标注行号必须是符号定义行（对应第 12 节的口径缺陷）。
