# 证据包格式与重放（Schema 2.0）

证据包保存本次运行选择的材料和测试结果。`verify` 分别报告材料核验、重放一致性和修复结论；重放 PASS 本身不代表修复 VERIFIED。

## 1. 目录和 JSON Schema

默认写入被修仓库的 `.replens/provenance/<UTC时间-随机ID>/`，每次新建目录，避免覆盖历史记录：

```text
manifest.json              必需文件的字节 SHA-256 清单（最后写入）
provenance.json            schema_version、源码清单、环境、补丁、套件位置和修复结论
report.json                本次结构化报告
report.md                  本次 Markdown 报告
patch/patch.json|patch.diff 有补丁时保存原字节，另在 provenance.json 内嵌文本
suites/primary.json        主命令、超时、附加文件内容和前后结构化结果
suites/auxiliary.json      自动生成检查的完整代码、命令、超时和前后结果
suites/acceptance.json     冻结独立材料的完整文件内容、命令、哈希、超时和前后结果
```

机器可读规范见 [provenance-2.0.schema.json](provenance-2.0.schema.json)。根 Schema 用于 `provenance.json`；`$defs` 中的 `manifest`、`primary`、`auxiliary` 和 `acceptance` 分别用于其他 JSON 文件。核心保持零第三方依赖，通过 `provenance.py` 校验字段和材料之间的关系，不需要安装 jsonschema。

`provenance.json` 顶层字段为 `schema_version`、`created_at`、`source`、`environment`、`issue`、`insufficient_evidence`、`repair`、`patch`、`suites`、`reports`。其中：

- `source.files` 保存规范相对路径到文件字节 SHA-256 的映射；`tree_sha256` 是聚合值。`root` 和可选的 Git 提交值用于追溯，不要求重放路径相同，也不以 Git 提交替代内容核对。
- `environment` 保存 Python 版本、实现、平台、解释器路径和已安装发行包版本。重放要求版本、实现、平台和发行包版本清单一致；解释器路径可变。
- `repair` 保存统一验收的 `status`、`reasons`、完整 `validation` 和补丁说明。没有补丁时 `patch=null`。

每个测试套件包含 `enabled`、`command`、`timeout`、`files`、`before`、`after`。`files` 的值是完整 UTF-8 源码文本，`before/after` 是结果列表或 `null`。辅助套件另有 `kind`，独立套件另有 `sha256`。未启用的套件使用空文件映射与 `null` 结果；启用但未执行（例如没有补丁）的独立套件仍保留完整冻结材料。

每条结果保存命令、退出码、框架、有效性、超时、通过标记、汇总、完整测试 ID/状态、无效原因及 stdout/stderr。日志沿用 `TestResult.to_dict()` 的各自末 4000 字符节选，不是完整原始日志；测试 ID 映射不截断。

## 2. 哈希定义与冻结顺序

1. 在索引、计划、生成候选之前读取仓库外的独立材料，并冻结到内存；同时冻结原始源码清单。打包时再次核对源码未变。
2. 源码按 `repo.EXCLUDE_DIRS` 排除 `.git`、`.replens`、虚拟环境及缓存目录；worktree 中包含机器专属路径的 `.git` 普通文件也排除，Git commit 单独记录。其他文件按原始字节计算 SHA-256。聚合时按相对路径排序，依次加入 `路径UTF-8 + NUL + 哈希ASCII + NUL`，因此内容相同的真实工作树可重建或移动。
3. 独立材料的冻结哈希沿用既有定义：`SHA256(json.dumps({command, files}, sort_keys=True, ensure_ascii=False).encode('utf-8'))`。外部 JSON 的缩进或键顺序不同，不改变冻结哈希；代码文本或命令不同会改变哈希。
4. manifest 对每个必需文件的实际字节计算哈希。独立材料的冻结哈希与 `suites/acceptance.json` 整个文件的字节哈希用途不同，均保留。
5. 候选选择完成后独立验收只在执行器的临时副本运行。打包器直接接收冻结的内存材料，不重新读取原材料路径，不将它混入主测试、索引、计划、提示词或候选反馈。`.replens` 目录不进入后续索引和执行副本。

## 3. Demo 生成和完整重放

在项目根目录运行，直接使用项目已有材料：

```powershell
python -m replens run examples/demo_repo --issue "date string with surrounding whitespace fails to parse" --test-cmd "python -m unittest discover -s tests" --auto-patch --acceptance-suite examples/acceptance/demo.json --require-verified --format json --output reports/runs/demo_verified.json
```

复制运行输出的实际证据包路径，替换下面的 `<证据包路径>`：

```powershell
python -m replens verify examples/demo_repo --provenance "<证据包路径>" --require-verified --format json --output reports/runs/demo_replay.json
```

重放直接使用包内主测试附加文件、生成检查和独立材料，不依赖原验收 JSON 文件。源码仍需另行保留，并与冻结清单完全一致。默认复用包内各套件的命令和超时；可选 `--test-cmd` 只能与冻结主命令一致，`--timeout` 可显式调整重放超时。

核验通过后，主测试、辅助检查和独立验收分别运行修复前/后。各阶段使用干净副本，复用既有执行器和 `assess_repair`，不重新选择候选、不调用模型。逐条比较命令、退出码、框架、有效性、通过标记、超时、完整测试 ID/状态和汇总；不比较包含随机临时路径及耗时的日志文本。目标 ID、原有 PASS ID、独立目标和冻结哈希也必须一致。

## 4. 三层结果和退出码

| 字段 | 含义 |
|---|---|
| materials_status | PASS：材料、源码和环境核验一致；FAIL：不能核验；LEGACY：历史旧包；NOT_CHECKED：尚未执行 |
| replay_status | PASS：各套件前后结果与统一结论一致；FAIL：不一致或未完成；NOT_RUN：未重放 |
| repair_status | VERIFIED / UNVERIFIED / FAILED / INVALID / NO_PATCH；不能评估时 NOT_EVALUATED |

未提供独立材料时，主测试通过的包可以 `replay_status=PASS`，同时保持 `repair_status=UNVERIFIED`。没有补丁和未应用的补丁也可形成一致的 NO_PATCH / FAILED 记录。

`verify` 默认在整体 `status=PASS` 时退出 0；材料或重放失败、旧包退出 1。加 `--require-verified` 后，重放一致但修复非 VERIFIED 退出 2。`run` 打包失败会保存可用修复报告并明确显示 FAILED、返回 2；`--no-provenance` 则为 SKIPPED。

报告中的 `provenance.status` 表示打包 WRITTEN / FAILED / SKIPPED；刚生成的报告显示材料 NOT_CHECKED、重放 NOT_RUN。重放结果另存，不反写已冻结证据包。

## 5. 兼容与范围

1.0～1.3 包标记为 LEGACY，保留历史用途，不自动补齐材料、不执行不完整重放。需要从原始源码重新运行以生成 2.0 包。

本阶段验证使用合法的日期解析 Demo 和离线规则补丁，不能推导真实模型或真实开源项目的自主修复成功率。本机校验和可证明内容一致性，不是数字签名、测试质量认证或可信时间戳。发行包版本清单不是环境锁定或包文件内容证明；需要自行准备相同依赖。临时副本提供文件隔离，不构成对任意不可信代码的操作系统沙箱。

专项检查：`python -m unittest discover -s tests -p test_provenance.py -v`。Web HTTP 测试在缺少 FastAPI/HTTPX 时明确跳过；handler 逻辑检查不能替代真实 HTTP 验证。
