# ADR-005 CI 本地可验证

> 状态：已采纳
> 日期：2026-10-28
> 关联：[T-20261028-06](../../../project-os/任务/T-20261028-06-三缺口收口.md)

## 背景

仓库只有 `.github/workflows/ci.yml`，而远端是 `gitee.com/who-ask-my-name-fee/oss1028.git`。
GitHub Actions 不会在 Gitee 上执行，Gitee Go 未配置（`.workflow/` 不存在）。

结论：**CI 配置存在但从未运行过**。这比没有 CI 更危险——它给人一种「有 CI」的错觉，「CI 通过」这句话在本项目此前从未有证据支撑。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 配置 Gitee Go（`.workflow/`） | 平台原生 | 需仓库侧权限与平台套餐；本地无法事先验证配置正确性 |
| B. 镜像到 GitHub 仓库 | 可直接用现有 ci.yml | 需新建并维护第二个远端，与「单一真源」冲突 |
| C. 本地 CI 运行器，逐步执行同样命令并出报告 | 当天即可验证；跨平台；不依赖平台权限 | 不是真正的托管 CI，仍需人工触发 |
| D. 保持现状，文档标注「CI 未验证」 | 零成本 | 问题不解决 |

## 决策

选 **C**：`scripts/run_ci.py` 按 `ci.yml` 的同样顺序执行 8 个步骤，逐步记录退出码、耗时与输出尾部，写出 JSON 报告。
`ci.yml` 与 `STEPS` 一一对应，两边都标注「改动须同步另一处」。

同时把两件容易被漏的事固化为独立步骤：

- 第 1 步「环境自检」：让依赖版本问题在第一步暴露，而不是表现为 3 条看似无关的用例失败（2026-10-28 真实踩过）。
- 第 2 步「数据集口径校验」：让字段漂移在 PR 阶段就被拒绝。

## 后果

实测 8 步全部通过（本机 Python 3.10.11）：

| 步骤 | 退出码 | 耗时 |
|---|---|---|
| 1 环境自检 | 0 | 0.77s |
| 2 数据集口径校验 | 0 | 0.09s |
| 3 单元与集成测试 | 0 | 56.17s |
| 4 端到端演示 | 0 | 5.14s |
| 5 拒绝未验证修复 | 2（预期） | 4.81s |
| 6 检索评测 | 0 | 0.33s |
| 7 基线对比 | 0 | 0.30s |
| 8 Web 冒烟 | 0 | 0.78s |

- 收益：CI 的每一步现在都有本机执行证据；报告落 `reports/runs/ci_local_*.json`。
- 代价：仍是人工触发，不是每次推送自动跑。**托管 CI 依然没有真实运行记录**，文档不得声称「CI 通过」。
- 后续若要真托管：配置 Gitee Go 或镜像到 GitHub，届时以平台记录为准。
