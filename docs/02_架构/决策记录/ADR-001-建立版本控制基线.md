# ADR-001 建立版本控制基线

> 状态：已采纳
> 日期：2026-10-28
> 关联：[T-20261028-01 目录与状态梳理](../../../project-os/任务/T-20261028-01-目录与状态梳理.md)

## 背景

`repo/` 是唯一有交付证据的副本（`repo-control/manifest.json` 22 个 SHA256 全匹配），但它**没有任何版本控制**：

- 唯一一份工作副本，任何误删误改不可回滚；
- 与 `repo-oss/`（Gitee 仓库，落后一个阶段）无法比对，不知道哪边新；
- 55 个文件内容不同、57 个仅 repo 有、26 个仅 repo-oss 有，但无从判断方向。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 以 `repo-oss` 为真源，把 repo 的改动 cherry-pick 进去 | 保留 git 历史 | 无法先验证哪边新；repo-oss 上游还没提交，风险高 |
| B. 以 `repo` 为真源，`git init` 建基线，再整体覆写 repo-oss | 内容已被 manifest 认证；可先做全量证据比对再决定 | repo 的历史从零开始 |
| C. 两边并行维护 | 不动现状 | 继续分裂，问题不解决 |

## 决策

选 **B**。先 `git init` 给 `repo` 建基线（`2d0e80d`），再全量 SHA256 比对判定方向，最后整树覆写 `repo-oss`。

## 后果

- 收益：`repo` 具备可回滚能力；比对后有确凿证据证明 `repo` 是迁移后新版本（24 对迁移文件内容完全相同）。
- 代价：`repo` 的 git 历史从 2026-10-28 开始，更早的演进只能从 `变更日志.md` 与 `EXECUTION_LOG.md` 还原。
- 需同步：`.gitignore` 需补齐运行产物与控制材料排除；`repo-oss` 同步前必须打备份点。
