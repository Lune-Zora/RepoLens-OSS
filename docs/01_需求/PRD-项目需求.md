# PRD：项目需求

> 文件命名：docs/01_需求/PRD-项目需求.md
> 依据：`RepoLens-OSS_项目进展与赛题合规审查_2026-10-06`（审查报告），结合当前代码实际状态整理。
> 需求来源：用户提供的 2026-10-06 项目审查报告；申报方向「AI 开发工具与开源协作」。

## 目标与背景

- 要解决的问题：开源贡献新手面对陌生 Python 仓库的 Issue 时，缺少可复现、可验证、有代码证据的定位与修复辅助工具。
- 给谁用：Python 开源贡献新手（参赛定位：3 名计科大三学生团队）。
- 项目定位：**RepoLens-OSS：面向开源贡献的代码证据检索与测试验证式 AI 修复助手**。
- 关键约束：初赛作品提交截止 2026-10-15 20:00；核心包 replens/ 保持零第三方依赖；第三方模型、数据、组件必须如实披露来源、版本、许可与使用方式。

## 用户故事

- 作为开源贡献新手，我想要输入 Issue 描述后看到候选代码位置与证据，以便快速定位问题。
- 作为开源贡献新手，我想要系统生成受范围约束的补丁并自动运行测试，以便确认修复是否有效。
- 作为开源贡献新手，我想要看到明确的验证状态（复现没有 / 改了什么 / 跑了哪些测试 / 模型还是规则），以便决定是否采纳补丁。
- 作为评委或复查者，我想要可复核的运行证据包与原始日志，以便核验结果真实可复现。

## 需求（EARS 句式）

### 功能链路（目标设计，非当前全部已实现）

- 当用户提供本地 Python 仓库路径，系统应识别许可证、依赖文件、测试框架，并生成源码与文档清单。
- 当仓库导入完成，系统应构建 AST + SQLite FTS5 索引；索引输入应统一排除 `.replens`、`.git`、缓存、虚拟环境、构建目录等运行产物。
- 当用户提供 Issue 或复现输入，系统应先固定环境并复现失败，记录 before 测试结果。
- 当失败测试与执行轨迹可用，系统应结合 Issue 进行结构与文档检索，返回带文件、行号、代码、来源与相关度的证据列表。
- 如果证据不足，则系统应拒答或请求补充复现输入、测试或日志，不得强行给出根因。
- 当证据足够，系统应由真实模型生成语义解释、修改计划与候选补丁，并记录模型来源、版本与候选顺序。
- 当生成补丁，系统应校验修改范围：默认仅允许证据白名单内的生产源码，拒绝测试文件、测试配置与命令被修改。
- 当候选补丁生成，系统应在临时工作区运行候选筛选测试；失败且有剩余预算时，应把该轮补丁与失败日志反馈给模型重试。
- 当候选通过筛选，系统应运行冻结的独立保留测试与原有回归测试，并以 fail→pass 作为修复成功判据。
- 当测试完成，系统应输出与轮次对应的报告（计划、证据、diff、测试 ID、状态）与可重放证据包。
- 当 `REPLENS_REQUIRE_LLM=1`（严格模型模式），系统应拒绝规则回退代替模型结果，并保留失败原因；允许回退的演示模式应明确标注规则来源。
- 当未配置模型，系统应仅提供规则演示能力，不得把规则修复计为模型成功。

### 结果状态

- 系统应在报告与界面区分：模型修复在指定测试范围内通过 / 规则演示修复通过 / 定位成功但修复失败 / 证据不足 / 环境错误 / 没有采集到有效测试。

## 非功能需求

- 性能：评测记录总耗时、请求数、候选数；不用首次成功耗时代替总成本。
- 安全：补丁路径边界校验、命令白名单、超时控制、临时副本执行；公开部署前需容器或受限进程隔离、鉴权与根目录约束。
- 兼容：Python ≥3.9；pytest 与 unittest 双框架端到端可验证；真实历史仓库按对应版本另建环境。
- 可用性：README 保持 5 分钟可读懂；Web 界面让新用户完成「选仓库 → 看失败原因 → 看补丁 → 看报告」全流程。
- 合规：第三方资源精确披露来源、版本、许可与使用方式；未核实的资源不得标为「已核验」。

## 现在的问题（缺口清单）

> 来源：审查报告第 6 节。每条含现象、修正方向、验收要点。

| 编号 | 问题 | 修正方向 | 验收要点 |
|---|---|---|---|
| P1 | 索引输入混入自身运行产物 | 统一排除策略（.replens/.git/缓存/虚拟环境/构建目录），生成材料写目标仓库之外 | 相同源码两次 run 前后索引清单与符号数一致 |
| P2 | 严格模型模式存在回退路径 | 计划与补丁层统一模式；严格模式拒绝规则代替模型 | 连接失败/超时/空 JSON/错误 JSON/错误补丁均明确失败或拒答 |
| P3 | 反馈执行顺序错误 | 先复现、提取轨迹，再检索计划；每轮快照不可覆盖；CLI 与 Web 共用同一编排 | 失败轨迹先于首轮补丁；第二轮包含上一轮真实补丁 |
| P4 | 重试状态错误 | `last_patch_content` 初始为空且赋值分支错误 | 重试请求包含上一轮实际补丁内容 |
| P5 | 测试适配与成功判定不可靠 | pytest/unittest 统一适配；冻结测试 ID、数量、skip/xfail；禁止删除或跳过失败断言 | 两框架各一条完整路径；缺包/零收集/超时不误判成功 |
| P6 | 补丁范围约束未完全落实 | 证据文件白名单作为真实校验参数；保护测试与测试配置；JSON 与 diff 两条入口都校验 | 范围外路径与测试配置被拒绝，合法源码补丁可应用 |
| P7 | few-shot 答案进入提示词 | 示例与评测任务分离；冻结数据集与提示词版本 | 至少一个不在 few-shot 与规则范围内的真实问题 |
| P8 | 「证伪」与翻转预测表述过度 | 运行证据改称「执行轨迹辅助定位」；预测在 before/after 之前冻结 | 同一失败测试正确记录 fail→pass；未收集/跳过不算翻转 |
| P9 | 证据包被夸大为不可篡改证明 | 改称「可复核运行证据包」；绑定 commit、源码树哈希、环境、命令、测试 ID | 源码不一致/缺文件/命令不同/局部修改均明确失败 |
| P10 | 自动合规清单失实 | 资源状态改为「本次实际使用 / 可选未使用 / 计划接入 / 待核验」；更新旧文档失实声明 | 每项「已用/已验证」有对应产物或可重复记录 |
| P11 | 真实评测与微调没有闭环证据 | 区分定位 / 补丁验证 / 自主修复三种实验；LoRA 暂缓 | 真实样本可复现；参考补丁不进入模型输入 |
| P12 | Web、隔离与发布有交付缺口 | 验证新用户全流程；新目录安装运行；公开服务前完成隔离与鉴权 | 新目录克隆安装可运行；Web 关键路径可用 |

## 验收标准

- [ ] 相同源码两次完整 run，前后索引文件清单、符号数和固定配置检索结果一致。
- [ ] 严格模式在服务连接失败、超时、空 JSON、错误 JSON、错误补丁下均明确失败或拒答。
- [ ] 选择一个关键词会定位错误、失败轨迹可补充正确位置的案例，日志证明运行证据在首轮补丁生成前进入上下文。
- [ ] pytest 与 unittest 各有一条完整验证路径；回归测试修复前因目标 Bug 失败、修复后通过。
- [ ] 仓库内不在允许范围的文件、其他位置 `test_*.py`、测试配置及改变测试收集的补丁被拒绝。
- [ ] 证据包在源码不一致、必要文件缺失、测试命令不同、测试数不同和局部修改时得到明确状态。
- [ ] 每项「已用/已验证」声明能对应当前产物或可重复运行记录；未做训练不再声明自有 LoRA 权重。
- [ ] 新目录按 README 安装运行成功；模型/规则、失败/成功在界面中明确显示。

## 范围外

- 暂缓：LoRA 微调、多语言扩展、公共部署与自动 PR、OS 级沙箱（本地可信使用先行）。
- 不做：删除或弱化失败测试、把人工参考补丁计为模型成功、把规则 Demo 包装成通用修复、引用未核实附件当官方规定。
